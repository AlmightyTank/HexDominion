# v0.2 Slice A — Economy Foundation

## Money authority

`scripts/core/credits_account.gd` supplies the same `CreditsAccount` implementation for player and AI. Each faction's `EconomyState` owns a separate account; no faction can spend the other's money.

```gdscript
var economy := EconomyState.new(600.0) # Configurable starting funds; default 400.
economy.account.can_afford(150.0) # Preview only; never a substitute for debiting.
economy.account.try_spend(150.0, "Purchase") # Checks and debits synchronously.
economy.account.add_income(25.0, "Income")
var history := economy.account.get_history() # Defensive copy, oldest first.
```

Balances retain fractional credits so fixed-tick income is not truncated to whole credits. Amounts must be finite and nonnegative, with a maximum balance of 1e15 credits. Invalid inputs, insufficient funds and income exceeding the ceiling return false without changing balance or history. Zero-value operations succeed without a ledger entry. Invalid constructor funds produce a zero opening balance, never debt. No overdraft tolerance is applied: spending must be fully covered.

`EconomyState.credits` remains a compatibility property for existing HUD/setup code. Reads return account balance; assignments use a validated, logged balance adjustment. Negative or non-finite assignments are ignored. Gameplay purchases and income use `try_spend`/`add_income`, not direct balance arithmetic.

## Buildings and units

- Construction validates site, ownership, building kind and limits, then debits through the account before adding the structure.
- Training validates ownership, building compatibility and queue capacity, then debits through the account before enqueueing.
- Rejected purchases leave credits, structures, queues and ledger unchanged.
- Queues remain paid upfront. Completing training never charges again.
- Free scenario-start buildings remain setup grants through `add_building`, not purchases.
- Owned territory/HQ income credits the same account. Invalid simulation delta cannot corrupt money.
- AI uses the same economy, price tables, affordability checks and debit API as the player.

## Transaction history and persistence

Every actual change records an increasing transaction ID, type (`starting_funds`, `income`, `spend`, `adjustment`), reason, prior balance, signed amount and resulting balance. Build/train reasons identify the kind and hex. Failed attempts are not transactions and are not logged. Consecutive income with the same reason is aggregated until another transaction occurs; this retains the complete financial chain without a new row every physics tick. History is not truncated.

Named saves include both factions' opening funds, balances and ledgers. Loading validates the chain, monetary ranges and agreement with the saved credit balance before changing the live match. Existing version-1 balance-only saves remain supported: their current balance becomes the opening funds of a new ledger because historical transactions are unavailable. Restarts create fresh accounts and histories.

## Verification

The headless suite covers exact-balance purchases, overdraw/repeated debit rejection, fractional income, invalid/negative/NaN/infinite inputs, overflow, zero operations, defensive history copies, account persistence and invalid ledger rejection. Both factions have integration tests for construction, training, completion without double-charge, and income. Existing save/restart/AI skirmish regressions remain covered.

No transaction-history UI, power system, refunds, cancellation, repairs or selling is introduced in this slice.
